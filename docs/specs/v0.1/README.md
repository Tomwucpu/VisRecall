## 1. 为什么拆成四份 Spec

V0.1 跨捕获、存储、AI/检索、交付四个相对独立的子系统。拆成四份可独立运行、独立验收的阶段 spec，避免一份 16 周的巨型计划在前期锁死过多细节，也让每个阶段结束时都有可演示、可实测的产物。

| 阶段 | 周期 | 目录 | 目标 | 状态 |
|---|---|---|---|---|
| 01 捕获闭环 | W3–6 | `01-capture-loop/` | 桌面骨架、快捷键/悬浮球、冻结帧、窗口识别、覆盖层选区、裁剪入库、素材列表、拖放 | 已完成（有条件，2026-11-05） |
| 02 存储与详情 | W7–9 | `02-library-detail/` | 悬浮球三态与显示设置、缩略图、详情面板、备注/标签、原始内容复制、删除、保留策略、存储位置查看/打开/迁移、崩溃恢复 | 启动前细化 |
| 03 AI 与检索 | W10–13 | `03-ai-search/` | OCR、嵌入、VLM Provider、两阶段索引、查询解析、FTS+向量+RRF、chip、命中解释 | 启动前细化 |
| 04 打磨与交付 | W14–16 | `04-hardening-release/` | 多屏/DPI 矩阵、内存优化、离线降级、数据流向页、50 条查询评测、打包安装 | 启动前细化 |

阶段 0（W1–2）技术验证并入阶段 01 的前置任务组：D3D11 覆盖层、OLE 拖放、WebView2 内存。FTS/向量可用性与 ≤100 条检索验证在阶段 03 启动前完成。验证不通过时先调整方案，不进入后续业务开发。

### 阶段 02 启动前必须补齐（源自阶段 01 验收，2026-11-05）

阶段 01 的自动化门禁全绿、单屏 150% 主链路在目标机器上实测通过，但下列项**没有**
在本机条件下验证到。它们不阻塞阶段 02 的开发，但必须在阶段 02 交付（或进入阶段 04
打磨前）补齐并回填 `01-capture-loop/verification.md`：

- [ ] **物理 4K 面板 + PresentMon 交叉验证**：在 4K 屏机器上重跑 Task 10 的场景 B/C，
      并用 PresentMon 对齐进程内 QPC 帧时间（当前 4K 全部为合成窗口）。
- [ ] **双屏与混合 DPI**：双屏同 DPI、150%+100%、负坐标/竖直错位；覆盖层控制点临空边、
      标签归属、跨屏拼合、`Present(1,0)/(0,0)` 分支目前只有单测。
- [ ] **单屏 100% / 125% / 200% 缩放**：本轮只覆盖 150%（100% 未测）。
- [ ] **物理 OLE 四来源拖放**：Chrome 文字、Word 文本、资源管理器图片、微信图片；
      现有证据是真实 OLE 管线（真实剪贴板 + `DoDragDrop` + `RegisterDragDrop`）。
- [ ] **DRM 视频 / 独占全屏**：全黑帧 → `DRM_PROTECTED` 目前只有假帧单测。
- [ ] **提权窗口与 UIPI 拖放**：高完整性级别下的捕获、热键与拖放行为。
- [ ] **实时模式决策**：阶段 01 抓帧失败直接 `CAPTURE_FAILED`（已确认降级）；
      阶段 02 评估是否实现「透明覆盖层 + 提交时现场抓取」。
- [ ] **托盘内存与空闲 CPU 按门禁口径测量**：本轮为一次快照 + 60 s 短采样，
      门禁要求是关闭主窗口 60 s 后的私有工作集与 10 分钟 PerfMon 空闲 CPU。
- [ ] **列表视觉验收**：100 条以内滚动流畅度、`加载更多` 反复翻页、状态徽标
      `解析中 → 正常` 的可见过渡（本轮均为视觉抽查，无帧率量化）。
- [ ] **打包产物**：阶段 01 未执行 `pnpm tauri build`；`cargo build --release` 的二进制
      仍指向 `devUrl`，只有启用 `tauri/custom-protocol` 才内嵌 `dist/`。打包配置与
      release 产物验收放入阶段 02 交付任务。
- [ ] **30 分钟连续使用 + ≥20 次真实捕获**（requirements §5 退出条件 2）：本轮只做了
      6 次成功捕获，进程累计约 21 分钟无崩溃。

## 3. 全局约束

每个阶段的任务都隐含以下约束：

- 仅 Windows 10 22H2（19045）及以上、Windows 11；x64 优先，ARM64 在阶段 04 单独验证。
- 单进程 `visrecall.exe`；UI 线程不做同步 IO/OCR/网络。
- 数据全本地、明文、用户可见目录；默认离线可用，云端模型是可选增强。
- 检索测试素材规模 **≤100 条**；不做万级压测与容量评测。
- 不实现本地 VLM；离线/无 Key 用 OCR 摘录降级（阶段 03 落地）。
- 托盘常驻内存目标 40–70MB，硬上限 150MB；空闲 CPU <1%。
- 捕获入口响应 ≤150ms；选区交互 60fps；提交到可检索 ≤3s（P95）。
- 所有外部请求必须带超时与取消；API Key 只存在 Rust 侧，前端拿不到。
- 依赖锁 `Cargo.lock` / `pnpm-lock.yaml`；升级前跑完整测试。

## 4. Spec 使用方式

每个阶段目录包含：

- `requirements.md`：范围、用户故事、可验收需求（带 ID）、明确不做。
- `design.md`：模块/文件结构、关键类型、线程与数据流、失败降级、测试策略、风险与门禁。
- `tasks.md`：按依赖排序的可勾选任务；每个任务含文件、接口、步骤、验证命令与提交点。

执行规则：

1. 先读 `requirements.md` 确认范围，再读 `design.md` 确认接口，最后按 `tasks.md` 顺序执行。
2. 每个任务结束必须跑该任务列出的验证命令；不通过不进入下一任务。
3. 阶段退出时更新本文件中的状态，并在阶段目录记录实测结果。
4. 需求变化先改 spec，再改代码；不在实现中悄悄扩大范围。

## 6. 阶段交付定义（DoD）

一个阶段只有同时满足以下条件才算完成：

- `requirements.md` 中所有 P0 需求有对应实现或明确的降级路径。
- `tasks.md` 全部勾选，验证命令通过。
- 手工验收清单在目标机器上跑过，结果记录在阶段目录。
- 没有未登记的临时绕过、硬编码路径或未锁依赖。
- 阶段产物可独立运行，不依赖下一阶段才能演示。
