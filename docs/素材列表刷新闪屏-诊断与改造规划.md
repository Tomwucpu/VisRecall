# 素材列表刷新闪屏 — 诊断与改造规划

> 日期：2026-11-19  
> 范围：仅前端素材网格（`src/features/library`、`src/lib/events.ts`、`src/app/App.tsx`）及事件失效策略；不改后端行为即可完成 P0/P1。  
> 状态：**P0 / P1 已实施，P2 部分实施**（2026-11-20）。实施记录见 §14；剩余项为事件合并、缩略图版本解耦、检索结果同步。
> 结论先行：**闪屏不是渲染性能问题，而是缓存策略问题。**「删除/修改素材后整块网格消失再回来」的根因是事件层对所有列表事件调用 `resetQueries`：它会把分页数据清成 `undefined`，让 `isPending` 变真，`ItemGrid` 于是把整个 `<ul class="grid">` 换成一行加载文案。已加载的多页数据同时被丢弃，只剩第一页重取，所以看起来像「重新渲染、重新排列」。

## 1. 现象拆解

用户看到的三个症状，其实是同一条链路上的三层后果：

| 症状 | 直接原因 |
| --- | --- |
| 闪屏 / 白一下 | 列表数据被清空 → `isPending` → 整块网格卸载 → 缩略图 `img` 全部销毁 |
| 排列乱了 / 跳回顶部 | `.grid-scroll` 内容高度瞬间塌陷 → `scrollTop` 被夹回 0；滚动容器还带 `scroll-behavior: smooth` |
| 只剩很少几条 / 要重新「加载更多」 | `resetQueries` 丢弃 `pages` 与 `pageParams`；重取时旧页数已为 0，只拉第一页 |
| 详情面板突然变空、正在写的备注/正文消失 | 列表瞬时为空 → `visibleCards` 为空 → `selected` 变 `null` → `DetailPanel` 被卸载，组件内草稿随之丢失 |

后两条影响比「闪一下」更严重：**数据丢失感**（分页位置、未保存草稿）才是用户真正会抱怨的点。

### 2.1 `resetQueries` 到底做了什么（已核对依赖源码）

`@tanstack/react-query@5.105` 中：

```js
resetQueries(filters, options) {
  matched.forEach((query) => query.reset());   // data → undefined，回到 initial state
  return this.refetchQueries({ type: "active", predicate: … });
}
// query.reset(): this.destroy(); this.setState(this.resetState);
```

而无限查询的 refetch 分支是「把旧页数当作要重取的页数」：

```js
const oldPages = context.state.data?.pages || [];   // reset 后是 []
const remainingPages = pages ?? oldPages.length;    // → 0
do {
  … fetch page …
  currentPage++;
} while (currentPage < remainingPages);             // 只执行一次 → 只取第 1 页
```

所以一次删除的实际时序是：

1. `api.deleteItem()` 成功，后端发 `item_deleted`；
2. `resetQueries(["items"])` → 缓存 `data` 变 `undefined`；
3. `ItemGrid` 收到 `isPending=true` → 返回 `<p>正在加载素材…</p>`，`<ul class="grid">` 被卸载；
4. `.grid-scroll` 内容塌陷 → `scrollTop` 归零（且 `scroll-behavior: smooth` 会把它做成一次动画）；
5. `visibleCards=[]` → `selected=null` → `DetailPanel` 卸载为 `DetailEmpty`；
6. 重取第 1 页（50 条）→ 网格重新挂载；之前加载的第 2、3… 页全部消失；
7. 所有 `img` 重建，`loading="lazy"` 的图片在可视区外要等滚动才重新解码。

### 2.2 排序本身没有不稳定

后端列表排序是 `ORDER BY i.captured_at DESC, i.rowid DESC`（[items.rs:104](file:///E:/project/graduation/VisRecall/crates/library/src/items.rs#L104)），带 `rowid` 兜底，结果稳定。所见「重排」不是 SQL 平局导致的，而是**页被丢弃 + 窗口回到顶部 + DOM 全量重建**共同造成的错觉。

### 2.3 为什么「任意编辑保存」都会闪：重索引回执

这不是「重建索引本身很慢」导致的，而是**重建索引完成后的回执事件**又踩中了同一颗雷。

所有可编辑内容（备注、标题、AI 描述、OCR、正文、标签）都走同一条写路径：

```text
用户保存
  → library.set_*() 写库
  → notify_metadata_changed([id])                    // hooks.rs:35
  → 元数据钩子 bump_revision_and_enqueue(index)       // pipeline_host.rs:363
  → 索引任务异步执行
  → index handler 完成三写后 emit item_indexed        // index.rs:109
  → 前端 events.ts: item_indexed → resetQueries(["items"])   // events.ts:270
  → data 清空 → isPending → 网格卸载 → 闪白 + 回到顶部
```

对应关系：

| 编辑动作 | 立即事件（不会清空列表） | 稍后触发的重索引回执 |
| --- | --- | --- |
| 备注 | `item_note_updated` | `item_indexed` |
| 标题 | `item_renamed` | `item_indexed` |
| AI 描述 | `item_content_updated(summary)` | `item_indexed` |
| OCR 文本 | `item_content_updated(ocrText)` | `item_indexed` |
| 正文 | `item_content_updated(bodyText)` | `item_indexed` |
| 标签增删 | `item_tags_updated` + `tags_changed` | `item_indexed` |

三个容易误判的点：

1. **备注保存的注释写着「不惊动列表」**（[app.rs:661](file:///E:/project/graduation/VisRecall/crates/app-core/src/app.rs#L661)），它自身确实只发详情事件；但写库后的元数据钩子会入队重索引，几百毫秒内补发 `item_indexed`，于是列表照样被清空。
2. **重命名的 `invalidateQueries` 也没用**：`item_renamed` 不闪，但紧随其后的 `item_indexed` 会闪。
3. **即使把索引优化到 0 ms，只要 `item_indexed` 还走 `resetQueries`，闪屏就不会消失。** 问题在回执的处理方式，不在索引耗时。

因此用户感知到的「保存后先正常、过一小会儿白一下并回顶」，正是「同步写入 → 立即详情事件 → 异步索引回执 → 整表 reset」的时间差。

### 2.4 附带问题：`revision` 被复用为缩略图版本号

`thumbUrl` 的缓存失效参数直接取 `items.revision`（[ipc.rs:84](file:///E:/project/graduation/VisRecall/src-tauri/src/ipc.rs#L84)），而每一次编辑都会 `bump_revision`。结果是：**改一段备注也会让该条卡片的缩略图 URL 变化**，列表重取后该卡图片会重新请求、重新解码一次。

即使把列表刷新改成局部 patch，只要 patch 回来的 `thumbUrl` 带了新 `rev`，这张卡仍会单独闪一下。建议在后续把「缩略图版本」与「索引 revision」解耦（新增 `thumb_revision`，只在缩略图真正重写时递增）。

| 编号 | 根因 | 影响 |
| --- | --- | --- |
| R1 | 列表事件使用 `resetQueries`，主动清空 `data` | 触发 `isPending`，网格整块卸载 → 闪屏 |

| R4 | `item_indexed` / `item_enriched` 是**逐条**事件（[pipeline_host.rs:240](file:///E:/project/graduation/VisRecall/crates/app-core/src/pipeline_host.rs#L240)），每条都 reset | 导入 100 张图 → 数百次整表重建 |
| R5 | 列表瞬时为空会把详情面板一并卸载 | 详情消失 + 备注/AI 描述/原文/OCR 未保存草稿丢失 |
| R6 | 筛选切换使用新的 `queryKey`，没有 `placeholderData` | 切换筛选/标签/时间同样白一下 |

## 5. 改造目标

### 5.1 目标

1. 任何单条/批量增删改，**列表 DOM 不卸载**、滚动位置不丢、已加载分页不丢。
2. 事件只更新受影响的那一条（或最少的查询），不再整表重建。
3. 详情面板在后台刷新期间保持可见，未保存草稿不因无关事件丢失。
4. 筛选/检索视图与全部素材视图的刷新语义保持一致。
5. 导入/解析批量事件下不产生「事件风暴式」刷新。

### 5.2 非目标

- 不引入虚拟滚动（当前 ≤100 条/页，暂不需要）。
- 不改后端排序、分页协议。
- 不重写检索链路（只修删除/重命名后结果不刷新的可见问题）。
- 不做多窗口缓存同步（当前单窗口）。

## 6. 方案总览

**核心原则：列表查询永远不用 `resetQueries`。**
数据只允许三种变更方式，优先级从高到低：

```
① 局部 patch（首选）  setQueriesData 按 id 原地替换一条
② 保留式失效（兜底）  invalidateQueries：data 保留，stale 期间后台重取
③ 禁止                resetQueries：只在「用户主动要求重置」时使用（当前产品里没有这种场景）
```

```
                   ┌──────────────────────────────┐
后端事件 ──► 路由   │ item_updated/indexed/enriched │──► ① getItem(id) → patch 一条
                   ├──────────────────────────────┤
                   │ item_renamed                 │──► ① patch title（不再重取全部页）
                   ├──────────────────────────────┤
                   │ item_deleted                 │──► ① 从所有缓存页移除该 id
                   ├──────────────────────────────┤
                   │ item_created                 │──► ② 失效（新条目位置/筛选匹配需后端判定）
                   ├──────────────────────────────┤
                   │ items_deleted/pruned/reset   │──► ② 失效（批量入口可再用已知 ids 做 ①）
                   └──────────────────────────────┘
```

分三期落地：**P0 止血（小 diff，先消除闪屏）→ P1 精确更新（消除整页重取）→ P2 体验打磨**。

## 7. P0：止血（建议先合入）

目标：改动尽量小，但保证任何事件都不再清空列表数据。预计 30–60 行。

### 7.1 事件层：`resetQueries` → `invalidateQueries`

[events.ts:204](file:///E:/project/graduation/VisRecall/src/lib/events.ts#L204) 的 `LIST_EVENTS` 分支、`items_deleted` 分支（[events.ts:192](file:///E:/project/graduation/VisRecall/src/lib/events.ts#L192)）、`item_indexed/item_enriched` 分支（[events.ts:270](file:///E:/project/graduation/VisRecall/src/lib/events.ts#L270)）统一改为：

```ts
const invalidateLists = (client: QueryClient) => {
  void client.invalidateQueries({ queryKey: queryKeys.items });
  void client.invalidateQueries({ queryKey: ["items-filtered"] });
};
```

注意：

- `invalidateQueries` 默认 `refetchType: "active"`，**data 不会变 undefined**，`isPending` 不会变真，网格不卸载。
- 无限查询 refetch 是「从第 1 页起按当前页数逐页重取」，且下一页游标用「新第 1 页的最后一项」重新推导（已核对 `infiniteQueryBehavior.js`）。因此增删后可能出现页边界重叠，但 `flattenItemPages` 已按 id 去重，**不会丢项也不会重复显示**。
- 同时失效 `["items-filtered"]` 顺带修掉 R8。

### 7.2 其它入口

- `ImportDialog` 新建文字后的 reset（[ImportDialog.tsx:199](file:///E:/project/graduation/VisRecall/src/features/import/ImportDialog.tsx#L199)）→ invalidate。
- `ImportSourcesPane` 移除来源后的 reset（[ImportSourcesPane.tsx:69](file:///E:/project/graduation/VisRecall/src/features/settings/ImportSourcesPane.tsx#L69)）→ invalidate。
- `SettingsDialog` 清理/清空只 invalidate 了 `items`（[SettingsDialog.tsx:265](file:///E:/project/graduation/VisRecall/src/features/settings/SettingsDialog.tsx#L265)、[SettingsDialog.tsx:301](file:///E:/project/graduation/VisRecall/src/features/settings/SettingsDialog.tsx#L301)），补上 `["items-filtered"]`。

### 7.3 UI 防御

- `ItemGrid`：把「pending 就整块替换」改成「**从未有过数据**才显示整块 loading」；已有数据时最多显示一条细刷新提示。这样即使未来又有入口误清缓存，也不会白屏。

```tsx
if (isPending && items.length === 0) return <p className="hint">正在加载素材…</p>;
// 有数据时保持网格，可用 isFetching 在顶部画一条 2px 进度条
```

- `App.tsx`：详情选中项加一层「上次选中卡片」兜底。列表因任何原因瞬时为空时，详情继续渲染上一份数据；只有确认该 id 已从非空列表消失时才关闭。

```tsx
const selectedCardRef = useRef<ItemCardData | null>(null);
if (selected !== null) selectedCardRef.current = selected;   // 渲染期同步或 effect
const shown = selected ?? selectedCardRef.current;
```

### 7.4 事件合并（可选但强烈建议）

`item_indexed` / `item_enriched` 在批量导入时是逐条发出的。即使只 invalidate，也会触发多轮「逐页重取」。加一个 200–300ms 的尾随合并：

```ts
let timer: number | undefined;
const scheduleInvalidateLists = (client: QueryClient) => {
  window.clearTimeout(timer);
  timer = window.setTimeout(() => invalidateLists(client), 250);
};
```

### 7.5 P0 效果

- 闪屏消失：列表数据始终存在，DOM 不卸载。
- 分页不丢、滚动不丢。
- 详情面板不再因无关事件被卸载。
- 代价：每次事件仍会重取全部已加载页（N 次 IPC）；重命名/状态变化仍属于「全量刷新」。P1 解决。

## 8. P1：按 id 精确更新

目标：一次事件只改一条卡片，**不产生任何列表翻页请求**。

### 8.1 抽出共享缓存工具

新增 `src/lib/itemCache.ts`（同时把 `toItemCardData` 从 `useItems.ts` 移到纯映射模块，避免 `lib → features` 的反向依赖）：

```ts
import { commands, type ItemDto } from "./bindings";
import { queryKeys } from "./queryClient";
import { toItemCardData } from "./itemDto";
import type { ItemCardData } from "../features/library/ItemCard";

type Pages = { pages: ItemCardData[][]; pageParams: unknown[] };

/** 返回原引用表示未命中，React Query 不会触发重渲染。 */
function patchPages(data: Pages | undefined, id: string, next: ItemCardData): Pages | undefined {
  if (!data) return data;
  let changed = false;
  const pages = data.pages.map((page) => {
    const index = page.findIndex((item) => item.id === id);
    if (index === -1) return page;
    changed = true;
    const copy = page.slice();
    copy[index] = next;
    return copy;
  });
  return changed ? { ...data, pages } : data;
}

export function patchItemEverywhere(client: QueryClient, next: ItemCardData) {
  client.setQueriesData<Pages>({ queryKey: queryKeys.items }, (data) =>
    patchPages(data, next.id, next),
  );
  client.setQueriesData<Pages>({ queryKey: ["items-filtered"] }, (data) =>
    patchPages(data, next.id, next),
  );
}

export function removeItemsEverywhere(client: QueryClient, ids: ReadonlySet<string>) {
  const strip = (data: Pages | undefined) => {
    if (!data) return data;
    let changed = false;
    const pages = data.pages.map((page) => {
      const kept = page.filter((item) => !ids.has(item.id));
      if (kept.length === page.length) return page;
      changed = true;
      return kept;
    });
    return changed ? { ...data, pages } : data;
  };
  client.setQueriesData<Pages>({ queryKey: queryKeys.items }, strip);
  client.setQueriesData<Pages>({ queryKey: ["items-filtered"] }, strip);
}

/** 取单条最新 DTO；NOT_FOUND 返回 null，调用方按删除处理。 */
export async function fetchItemCard(id: string): Promise<ItemCardData | null> {
  try {
    return toItemCardData(await commands.getItem(id));
  } catch {
    return null;
  }
}
```

要点：

1. **必须保留 `pageParams`**，只改 `pages`；否则后续 `fetchNextPage` 游标会断。
2. 未命中时返回原对象引用，配合 React Query 默认的结构共享，`ItemGrid` 与 memo 后的卡片都不会重渲染。
3. `commands.getItem` 已返回带 `preview` 的 DTO（[ipc.rs:847](file:///E:/project/graduation/VisRecall/src-tauri/src/ipc.rs#L847)），可一次补齐状态、缩略图、标题、预览。

### 8.2 事件映射（P1 最终形态）

| 事件 | 动作 |
| --- | --- |
| `item_updated` | `fetchItemCard(id)` → `patchItemEverywhere`；同时失效 `detail(id)`；若 `fields` 含 `status` 且当前有筛选视图，额外失效 `["items-filtered"]`（状态筛选的成员可能变化） |
| `item_indexed` | 同上（状态/缩略图变化）；这是**所有编辑保存后的延迟回执**，必须 patch 掉，不能再 invalidate/reset。注意 `rev` 变化会让 `thumbUrl` 变成新地址，见 R12 |
| `item_enriched` | 同上 + 失效 `detail(id)`、`tags`；自动标签可能改变标签筛选的成员，所以筛选视图用 invalidate 而不是只 patch |
| `item_renamed` | `fetchItemCard` → patch；**不再**失效 `["items"]`/`["items-filtered"]` |
| `item_content_updated(bodyText)` | `fetchItemCard` → patch（预览变化）；不再整表失效 |
| `item_deleted` | `removeItemsEverywhere(new Set([id]))` + usage/orphans/purgePreview |
| `items_deleted` | 优先由调用方（`App.deleteSelected`）在 API 成功后用已知 ids 立即 `removeItemsEverywhere`；事件自身作为兜底只失效列表（不再 reset） |
| `items_pruned` / `items_reset` | invalidate 两项列表（批量且无 ids，保留数据等待重取） |
| `item_created` | 失效两项列表（**不推荐前端强行插入**：目录导入的新条目 `capturedAt` 可能是旧时间，盲插顶部会排错；等 P2 有排序插入再做乐观插入） |

### 8.3 详情面板

- `item_updated/indexed/enriched` 后失效 `detail(id)`，让状态行、缩略图立即更新；`item_renamed`、`item_content_updated` 已覆盖。
- 详情查询本身是单条 `useQuery`，失效不会让 `DetailPanel` 卸载，只会短暂保留旧值再替换，可接受。

### 8.4 分页正确性说明

| 变更 | 是否安全 | 原因 |
| --- | --- | --- |
| patch 一条字段 | 安全 | `pages` / `pageParams` 不变 |
| 从任意页移除 id | 安全 | 删除的条目已不存在；后续游标仍指向原页边界；跨页重复由 `flattenItemPages` 去重 |
| 在首页插入一条且不裁剪 | 安全 | 首页会暂时多一条；`getNextPageParam` 取最后一页最后一项，边界不变，不会漏项 |
| 在首页插入一条并裁剪到 50 | **不安全** | 会挤掉原第 50 条，而下一页游标仍小于它，导致该条再也取不到 |
| 失效后重取全部页 | 安全 | refetch 会用新的第 1 页重新推导后续游标；可能重叠，但去重后无丢失 |
| 切换筛选条件 | 安全 | 新 `queryKey`，属于新查询 |

> 结论：**不要为了「保持 page size=50」去裁剪 patch 后的页。** 多出来的那一条在下次重取时会自然归位。

### 8.5 批量事件的可选后端增强

如果后续仍觉得逐条 `getItem` 的 IPC 数量偏高，再做（不阻塞 P0/P1）：

1. `item_updated` / `item_created` 事件载荷直接带 `ItemDto`，前端零请求 patch；
2. `items_deleted` 载荷带 `ids: string[]`；
3. 新增 `items_get_many(ids)` 批量读命令，前端按 200ms 窗口合并。

## 11. 风险与取舍

1. **P1 依赖 `commands.getItem` 逐条调用**：批量导入时 IPC 次数仍不低，但每次只读一条、不翻页；可先用 P0 的事件合并，后续再考虑后端把 DTO 塞进事件载荷。
2. **patch 与筛选成员判定**：前端无法可靠判断「新状态/新自动标签是否仍符合当前筛选」。因此 `item_updated(status)`、`item_enriched` 在**筛选激活时**保留 invalidate 兜底；筛选未激活时纯 patch。这是正确性优先的取舍。
3. **`item_created` 不做乐观插入**：导入文件的 `capturedAt` 可能早于当前列表，盲插顶部会排序错误。P0/P1 用「保留式失效」保证正确性；若后续要做，需要后端提供 `rowid` 或返回插入位置。
4. **结构共享**：patch 未命中和字段未变化时返回原引用，依赖 React Query 默认 `structuralSharing` 与 `memo` 才能完全避免重渲染；如果后续有人在 `queryClient` 里关掉 `structuralSharing`，这个优化会退化。
5. **`resetQueries` 的全面禁用**：目前代码里没有「必须丢弃分页」的产品场景；若未来出现（例如后端换了排序协议），应通过改变 `queryKey` 表达，而不是 reset。
6. **StrictMode 双订阅**：`subscribeAppEvents` 已有 `disposed` 保护（[events.ts:149](file:///E:/project/graduation/VisRecall/src/lib/events.ts#L149)），P0 的定时合并要注意在 `cleanup` 时清掉 timer，避免退订后仍触发一次刷新。

## 13. 一句话总结

闪屏来自「事件 → `resetQueries` → 清空分页 → `isPending` → 整块网格卸载」这一条链。把列表刷新从「重置」改为「保留数据 + 失效/局部 patch」，闪屏、丢页、滚动跳动和详情草稿丢失会一起消失；P1 再把粒度精确到单条，彻底消除不必要的整页重取。
